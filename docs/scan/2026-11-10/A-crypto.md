# A-crypto — PhantomVault cryptography & vault-persistence audit

- **Repo:** `phantom_vault`, HEAD `116f57a` (2026-11-07), read-only audit — no file under `src/` or `ui/` was modified.
- **Scope (assigned):** `src/crypto.rs`, `src/core/pq_hybrid.rs`, `src/core/memory.rs`, `src/storage.rs`, `src/storage/*`, `src/security/offline_cache.rs`, `src/error.rs`.
- **Adjacent files opened only to answer the nine checks:** `src/security/shredder.rs` (check 7 — it *is* the save primitive), `src/security/{app_pin,ext_pin,access_log,pq_profile}.rs` (checks 2/8), `src/models.rs` (check 4), `src/main.rs` (check 4), `src/attachment_store.rs` + `src/security/sharing.rs`/`secure_send.rs` (check 1 sweep).
- **Method:** every production line of the eight assigned paths read in full with line numbers; every AEAD construction site in the repo enumerated (11 total) and each nonce traced to its origin; every `.unwrap()`, `.expect(`, `panic!` and slice-index site classified as prod or test by the `#[cfg(test)]` boundary. No build, no fuzzing, no runtime measurement — findings are static-reading results.

## Severity summary

| Sev | Count | Meaning here |
|---|---|---|
| P0 data-loss / key-compromise | **0** | none found |
| P1 exploitable weakness | **0** | none found |
| P2 hardening | **11** | memory hygiene, latent Debug leaks, integrity edge cases, format hygiene |

The crypto core is sound: XChaCha20-Poly1305 with a fresh 192-bit random nonce per message, Argon2id at 64 MiB/t=3/p=4 with a per-save OsRng salt, HKDF domain separation, ML-KEM-768 encapsulation per save, verify-before-decrypt key unwrap, rev/prev-hash chain inside the AEAD, and tmp+fsync+rename saves. All eleven findings are second-order.

## Findings

| id | sev | file:line | what is wrong | concrete fix |
|---|---|---|---|---|
| A-01 | P2 | `src/storage.rs:487` (save), `src/storage.rs:682–740` (load) | The plaintext JSON envelope is never wiped. On save, `payload = envelope_bytes(...)` (487) is encrypted at 488 and then dropped as a plain `Vec<u8>`; on load, `decrypted` holds the complete vault as JSON — every password, TOTP secret, SSH private key — and is dropped unwiped on all five success returns (685, 691, 718, 722–738). The `Vault` itself is zeroized on drop, so the struct-level invariant (rules §1.2, and the "no lingering plaintext" comment at `models.rs:591`) is satisfied while the largest plaintext copy in the process is not. | Return `Zeroizing<Vec<u8>>` from `envelope_bytes`, or `let mut payload = ...; ...; payload.zeroize()` after the encrypt call, and `let decrypted = Zeroizing::new(decrypt...)` so every early return wipes. Same treatment for the `serde_json::from_slice`/bincode windows. |
| A-02 | P2 | `src/models.rs:593` — nested derives at `401, 425, 447, 476, 521, 546`; unredacted fields at `619, 629` | `pub struct Vault` **derives `Debug`** while holding key material. `Credential` (`318–330`) and `TotpAccount` (`372–381`) were correctly given hand-written redacting impls, but the aggregate is not: `{:?}` on a `Vault` prints `PaymentCard.card_number`/`cvv` (452/455), `SshKeyItem.private_key` (551), `PasskeyItem.private_key_pkcs8` (531), `IdentityItem.nid_or_passport` (481), `SoftwareLicense.license_key` (404), `SecureNote` (425) **plus** `Vault.totp_unlock_secret` (619, the unlock second factor) and `attachment_root` (629, the 32-byte root that wraps every attachment file key) as raw strings/byte arrays. Latent today — I grepped for `{:?}` on a vault/credential and found no production call site — but it is exactly the banned pattern in check 6 and one `dbg!` away from a key dump. | Drop `Debug` from `Vault` and from the item types (or hand-write redacting impls in the style of `Credential`), and mark `totp_unlock_secret`/`attachment_root` as `[redacted]`. |
| A-03 | P2 | `src/crypto.rs:190–194` (DK wrap), `315–318` (portable payload), `432–435` (paranoid payload) | No **AAD** on any container AEAD call: `cipher.encrypt(&nonce, plaintext)` passes `()`. Header fields are bound only *implicitly* — salt feeds Argon2id, `wrap_nonce`/`wrapped_dk` are the wrap ciphertext, `pq_ct` determines the HKDF salt — so a header-field swap changes the payload key and fails the tag. I traced cross-vault substitution explicitly, including the same-password case: single-field swap, whole-header swap, and header+ciphertext swap all fail closed. So this is **not** exploitable in the current layout, but the security argument is implicit and fragile (any future unkeyed header field, e.g. a KDF-parameter block, becomes malleable), and the project already does it correctly elsewhere: `attachment_store.rs:50–63` binds id+chunk-index as AAD. | For the next container version: `Aad::from(&[magic ‖ salt ‖ wrap_nonce ‖ pq_ct])` on the payload AEAD and `magic ‖ salt` on the DK wrap, both sides deriving AAD from the header (no layout change). Add a test that substitutes each header field and asserts failure — none exists today (the crypto tests only flip the last ciphertext byte, truncate, or use a wrong key). |
| A-04 | P2 | `src/crypto.rs:369–370` (most reachable), `299–304`, `377–378` | `?` early returns skip the manual `argon2_key.zeroize()`. At 369 the Argon2id key is derived from the typed master password, and 370 `unwrap_with_key(...)?` returns on **every wrong-password attempt** (and on a tampered `wrapped_dk`) before the `zeroize()` at 379 — so each mistyped unlock leaves a password-derived key in freed heap. Same shape at 299–304 (`PQ::combine`/`wrap_with_key` failing before `zeroize()` at 306) and 377–378. The manual call pattern is what makes this possible; note the V1 path at 150–154 was already fixed for exactly this bug. | Hold the derived key as `Zeroizing<[u8;32]>` (`derive_key_secret` returning it directly) so no early return can skip the wipe, and delete the hand-written `zeroize()` calls. |
| A-05 | P2 | `src/storage.rs:485` → `next_meta` `336–361` | `let old = fs::read(path).unwrap_or_default()` collapses "file missing" and "file unreadable" into an empty buffer. If the read fails transiently (AV/OneDrive/sharing violation) in a fresh process — i.e. `container_head()` is `None` — `next_meta` takes the first-save branch at 337–343 and returns `(1, "")`. The save then writes a container with **`rev = 1` and an empty `prev_hash`**, silently resetting the A16 anti-rollback chain: `check_incoming` (`182–214`) can no longer detect a fork or a skipped revision from this device, which is the one thing that chain exists to prevent. | Match on the error kind: only `ErrorKind::NotFound` may mean "first save"; every other error aborts the save with the original message. |
| A-06 | P2 | `src/storage.rs:639` | `fs::read(&file_path)` loads the whole container with **no size cap** before any length check. The 16 MiB limit at 711 applies only to the *decrypted* bincode payload, and *after* the file is already resident. A hostile or corrupted synced container (the sync path feeds this function) of multi-GB size aborts the process on allocation — release profile is `panic = "abort"`. | `metadata().len()` check (e.g. `> 64 MiB ⇒ Err`) before `fs::read`; the pad bucket is 1 MiB (`155`), so 64 MiB allows a very large vault. |
| A-07 | P2 | `src/security/shredder.rs:108–115` | `secure_write` leaks its temp file on the realistic error path: cleanup only runs in the `rename` closure (112–115), so a `write_all` (108) or `sync_all` (110) failure — disk full, quota — returns via `?` and leaves `vault.enc.<hex>.tmp` on disk forever, accumulating one ciphertext file per failed save with no sweeper. Also **no directory fsync** after the rename, so the rename itself may not be durable after a power cut (the file *content* is fsynced at 110 before the rename, so the live file is never torn and the old copy survives — no data loss). | RAII temp guard that deletes on every error path; after `rename`, flush the parent directory handle where the OS permits; sweep sibling `*.tmp` files on the next successful save. |
| A-08 | P2 | `src/security/ext_pin.rs:139–141` → `derive` at `71–80` | The only Argon2 parameters read from a file in the whole tree: `m`, `t`, `p` are parsed from the DPAPI-sealed `ext_pin.dpapi` text as bare `u32` with **no range check** and passed straight to `Params::new`. A record with `m = 4_294_967_295` requests ~4 TiB. Exploitability is low — producing a well-formed record requires the same Windows user's DPAPI key — but it contradicts the project's own "bound values from a file before use" stance, and this record is also parsed on the `cache_get` path (`offline_cache.rs:310`). | Reject `m ∉ 8..=1_048_576` KiB, `t ∉ 1..=16`, `p ∉ 1..=8` before `derive`; fall back to the compiled constants. |
| A-09 | P2 | `src/security/access_log.rs:294` | `if recomputed_hmac == hash` compares the HMAC chain link with `==` on hex `String`s — variable-time, with an early return. Verification is local-only over a file the attacker can already write, so there is no practical oracle, but it is inconsistent with `ext_pin.rs:185`, which does this correctly with `subtle::ConstantTimeEq`. | Hex-decode both sides and compare with `ct_eq`. |
| A-10 | P2 | `src/storage.rs:144–150` | `parse_envelope` validates `meta.format` but **never `meta.version`** (the constant is `CONTAINER_VERSION = 2`, line 21). A container written by a newer build parses as v2, unknown fields are silently dropped, and the next save rewrites it as version 2 — silent forward-compatibility data loss. The test at `1020–1040` (`json_ignores_unknown_future_fields`) asserts exactly this drop and treats it as correct. | `meta.version > CONTAINER_VERSION ⇒ Err("vault written by a newer version")` and open read-only at most; never re-seal a newer container as an older one. |
| A-11 | P2 | `src/security/offline_cache.rs:40` (derive), `45` (field), `214–231` | `CachedLogin` derives `Debug` on a struct whose `password: String` is **plaintext** (`45`) — the exact banned pattern, on the one type that holds decrypted logins for the extension. `CachedLogin::drop` (`53–59`) zeroizes the field, but `Clone` + derived `Debug` bypass that discipline. Separately, `entry_json` copies each password into a `serde_json::Value` (221) that is never wiped when the response `Value` is dropped. | Drop `Debug` from `CachedLogin`/`Snapshot` or hand-write a redacting impl; build the response by serializing directly into the output buffer rather than materializing a plaintext `Value` tree. |

## Verified good (with evidence)

1. **Nonce discipline — clean.** All 11 AEAD construction sites in the repo generate their nonce from OS entropy: `crypto.rs:103, 190, 314, 431, 592`; `attachment_store.rs:67, 110`; `sharing.rs:163`; `secure_send.rs:99, 300`; `emergency.rs:258`. No counter nonce, no nonce derived from a password or index, no persisted nonce re-used on re-save. A re-save generates a **new salt** (`crypto.rs:288`), a **new ML-KEM keypair** (291), a new wrap nonce (190) and a new payload nonce (314). A repo-wide grep for `thread_rng`, `SmallRng`, `StdRng::from_seed`, `seed_from_u64` returns nothing — `OsRng` only.
2. **Argon2id parameters are constants, never read from the container** — `crypto.rs:69–72`: `Params::new(64*1024, 3, 4, Some(32))`, `Algorithm::Argon2id`, `Version::V0x13`; 16-byte salt from `OsRng` at `95/288/457`. A hostile vault file therefore **cannot** inflate KDF memory (see A-08 for the one non-container exception).
3. **Verify before decrypt.** The DK unwrap is itself an AEAD open (`crypto.rs:201–217`), so a wrong password fails at the Poly1305 tag *before* any ML-KEM work — the claim in the comment at 202–203 holds. `decrypt_vault_paranoid_secret` (467–508) zeroizes the Argon2 key on both decapsulate-failure and combine-failure paths (490, 497, 501).
4. **Cross-vault key substitution fails closed.** The payload key is `HKDF-SHA256(salt = pq_secret, ikm = argon2_key)` over *all* header fields (`pq_hybrid.rs:145–152`), so a swapped salt/`wrap_nonce`/`wrapped_dk`/`pq_ct` changes the payload key. Same-password and whole-header swaps both fail the payload tag. (Hardening only: no explicit AAD — A-03 — and no test asserts this.)
5. **No silent paranoid→portable downgrade.** `check_profile` (`storage.rs:461–471`) requires the AEAD-protected `meta.profile` to match the container magic, and V3 has **no** fallback branch (`647–654`); the profile is resolved under the save lock (`482–484`). `convert_vault_profile` (`512–543`) is the only downgrade path.
6. **Replay/fork chain is inside the AEAD** — `envelope_bytes` (`163–179`) puts `rev`/`prev_hash` in the encrypted payload, `check_incoming` (`182–214`) refuses `rev < local` and requires `prev_hash == local_hash` for `rev > local`, and `next_meta` (`336–361`) refuses to reset a known head. Documented TOFU limit at 204–206 is honest.
7. **Proof-first destructive operations.** `rekey_vault_secret` (`561–618`) proves the old password opens the file, round-trips the new container, *and* verifies the old password cannot open it, before rotating or writing. Same pattern in `convert_vault_profile` (`528–537`).
8. **Atomic save + backup rotation.** `shredder.rs:88–117`: random temp name, `create_new` (no symlink/plant), write → flush → `sync_all` → `rename`; the live file is never torn. `rotate_backups` (`storage.rs:308–333`) shreds the oldest generation *first* so a crash can only leave an extra backup, never a missing one, and copies the old ciphertext to `.bak.1` before the replace — the old container cannot be lost to a mid-write death.
9. **Zeroize coverage at the type level is genuinely good.** `PqSharedSecret`, `HybridDerivedKey`, `PqDecapsulationBytes` are `Zeroize + ZeroizeOnDrop` and deliberately **not** `Debug` (`pq_hybrid.rs:21–50`); `Vault`, `Credential`, `TotpAccount` and every item type derive `Zeroize + ZeroizeOnDrop` (`models.rs:275, 352, 593`); `#[zeroize(skip)]` is used only on `item_tags`, correctly (`637–639`). `DpapiGuard` wipes the input copy and the `LocalAlloc`'d plaintext before `LocalFree` (`memory.rs:88, 141–150`); `LockedBytes` pins the real heap buffer and wipes+unlocks on drop (`200–230`). The master password lives as `SecretString` in `Arc<Mutex<Option<SecretString>>>` (`main.rs:1596, 1601`; accessor `985–988`) — no plaintext `String` master in the app layer.
10. **Novel-path KEM hygiene.** ML-KEM-768 keygen/encaps/decaps all take `&mut OsRng` (`pq_hybrid.rs:64, 128, 138`), lengths are checked before `from_bytes` (81–108), and a degenerate all-zero shared secret is refused and wiped (`110–118`).
11. **No panics on corrupt input in the assigned files.** Every header slice is length-checked before `XNonce::from_slice` (which panics on a wrong length): `crypto.rs:132–142`, `201–207`, `225–231`, `352–365`, `471–485`. No `.unwrap()`/`.expect()`/`panic!`/unchecked `[0]` appears in any production line of the eight assigned paths; the boundaries I used to separate test from prod code are `crypto.rs:512`, `core/pq_hybrid.rs:160`, `core/memory.rs:228`, `storage.rs:769`, `security/offline_cache.rs:350`, `security/shredder.rs:119`, `storage/backup_scheduler.rs:201`. All hits at or after those lines are test code and were ignored; non-panicking `unwrap_or*` was not counted.
12. **Error strings never interpolate secret material** — `crypto.rs:148, 216, 224, 380, 505` are constant messages; `error.rs` carries only `String` and no call site embeds a password or key. No `println!`/`eprintln!` of a secret in the app paths (the only `println!("password: …")` is `share_cli.rs:501`, an intentional CLI reveal command, outside this scope).

## Not verified / out of scope

- **Not dynamically tested.** I did not run `cargo test`, corrupt a real container, or measure unlock memory; no claim here rests on execution.
- **Not audited:** `src/importer/*` (a hostile `.kdbx` with attacker-chosen Argon2 `m_cost` is the classic sibling of A-08 and deserves its own pass), `src/sync/*`, `share*.rs`, `secure_send.rs`, `emergency.rs`, `shamir.rs`, `steganography.rs`, and the browser-extension JS.
- **Adjacent code-standard deviation, not a vulnerability:** `access_log.rs:108` uses `.expect("hmac key")` in a production function (unreachable — HMAC accepts any key length) and `share_cli.rs:501/509` deliberately print a password/TOTP to stdout for its CLI reveal command.
- **Test gap worth closing with A-03:** no test asserts that substituting `salt`, `wrap_nonce`, `wrapped_dk` or `pq_ct` between containers fails.
